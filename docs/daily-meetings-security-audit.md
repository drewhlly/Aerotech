# Meetings integration security audit — 19 November 2026

The old provider was hand-written Jitsi / 8x8 JaaS, not an AI agent SDK. Its browser loader, JWT signing branches, bearer guest implementation, CSP hosts, deployment instructions, fixture configuration and environment-template entries were removed or replaced. No old provider SDK dependency was installed. Existing API route names are intentionally retained behind authenticated Daily handlers to preserve portal and ATS links.

Current tracked source scan found no private-key block. Old provider variable names were found in two historical configuration documents and their obsolete setup rows were removed. Do not treat generic application encryption/session/Resend keys as retired meeting keys.

A scoped `git log --all -p` scan of reachable environment files, key files, meeting signing/guest handlers, deployment documentation and workflows examined 5,609 patch lines. No literal old-provider credential or private-key block was found in that scoped scan. A broader all-path history scan is incomplete because the repository lazily fetches historical blobs. This is not a clean bill of health for every historical blob, deleted remote branch, fork, cached build or deployment log; an all-history secret-free assertion cannot be made. If a historical credential is found, rotate/revoke it at the provider before considering history cleanup. No history was rewritten.

Stored hosting secrets are a separate scope. The production old provider configuration must be retained while that production deployment still serves meetings; this branch has no Daily account/key and has not replaced production. At verified Daily cutover remove the old Jitsi domain/app/secret/sub and JaaS app/key/private-key values from Vercel Production/Preview and the intended Cloudflare Worker, retire rollback deployments that still require them, then revoke old provider credentials. Their values must never appear in reports, logs or chat. Removal from source alone does not revoke a provider key.

Automated checks use disposable fake provider tokens and intercepted HTTP responses. They verify server authorization, invitation proof, cross-tenant denial, admission, short TTL, cancellation/reschedule revocation, calendar escaping, budget and rate controls. They do not prove real Daily API acceptance, two-device call quality or actual email receipt. Physical-provider acceptance remains required before live cutover.
